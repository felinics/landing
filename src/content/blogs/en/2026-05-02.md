# Introducing Memoh Discuss Mode — How We Built a More Proactive Group Chat Bot

In a typical chatbot workflow, you type a message, the bot finishes the job, and it returns a result. That pattern shows up everywhere — in agent apps and in agents bound to a messaging channel.

We first carried the same idea into group chats: mention the bot, wait for it to reply.

For a group, that is still too passive. We wanted the bot to join the conversation on its own, instead of waiting to be triggered. That is why we built Discuss mode.

:::tip
Memoh Discuss mode is based on [Menci](https://github.com/Menci)'s experimental project [Cahciua](https://github.com/Menci/Cahciua). Thanks to Menci for the open-source work in Memoh.
:::

How do you go from "speak only when @mentioned" to "decide whether to speak"? Split in two: first, how the bot *sees* everything in the group; second, how it decides whether to open its mouth.

## DCP: a deterministic context pipeline

For a bot to understand a group chat, you first have to turn the message stream into context an LLM can read.

The usual approach is to concatenate history into a messages array and dump it into the model. Group chat has details that 1:1 chat never has to handle: edits, deletes, display-name changes, joins and leaves, quotes, forwards. All of that changes what the bot should understand.

We introduced **DCP (Deterministic Context Pipeline)** and split context construction into three pure-function layers:

**Adaptation**: normalize raw events from Telegram, Discord, Lark, and other platforms into a single `CanonicalEvent`. This is an anti-corruption layer — whatever the upstream API looks like, the pipeline always sees the same data shape.

**Projection**: `IC' = Reduce(IC, Event)`. A pure state machine. Incoming messages append a node, edits mutate in place, deletes are marked, a rename inserts a system event. No I/O, no side effects, fully testable.

**Rendering**: `RC = Render(IC, RenderParams)`. Serialize IC into XML the LLM can read. Each message becomes a `<message>` tag. Identity (who sent it, when, which channel) lives in XML attributes, not in the body — so a user cannot forge identity through message text.

The bot sees context like this:

```xml
<message id="42" sender="Alice (@alice)" t="2026-05-02T14:30:00+08:00"
         channel="telegram" conversation="Dev Group" type="group">
How is the new prompt working for you?
</message>
<message id="43" sender="Bob (@bob)" t="2026-05-02T14:30:15+08:00"
         channel="telegram" conversation="Dev Group" type="group">
<in-reply-to id="42" sender="Alice (@alice)">How is the new prompt working for you?</in-reply-to>
Much better than before, though it still talks a bit too much
</message>
<message id="44" sender="Alice (@alice)" t="2026-05-02T14:31:00+08:00"
         channel="telegram" conversation="Dev Group" type="group">
<mention uid="bot123">@Memoh</mention> what do you think?
</message>
```

Quotes nest in `<in-reply-to>`, mentions use `<mention>`, attachments use `<attachment>`, edited messages get an `edited` attribute, and deleted messages become a self-closing `<message ... />`. All user text is XML-escaped and kept strictly apart from the tags. That is the anti-injection rule: the bot decides *who said it* from attributes, not from words in the body.

All three layers are pure. Same input, same output. The whole pipeline is predictable, replayable, and testable.

## Driver: the bot decides whether to speak

DCP answers "how to see." Whether to speak after seeing is not in the pipeline — it lives in the Driver.

The Discuss Driver is unlike Chat. In Chat, every message synchronously triggers an LLM call, and the bot must reply. In Discuss, an incoming message only pushes the latest rendered context (RC) into a channel and returns immediately — no blocking, no waiting.

A per-session goroutine consumes those RCs in the background. It does a few things:

1. **Coalesce updates**: a burst of messages does not mean a burst of LLM calls. It drains pending updates and uses only the latest RC.
2. **Check the trigger**: call the LLM only if there has been a new *external* message since the last turn — not something the bot said itself.
3. **Compose context**: merge RC (the user message stream) and TR (Turn Responses, the bot's previous LLM traces) by timestamp.
4. **Call the LLM**: system prompt, tool definitions, composed context, then `Agent.Stream()`.
5. **Advance the cursor**: after the call, move `lastProcessedMs` to the latest RC timestamp consumed in this turn. Messages that arrived during generation have later timestamps, so they naturally start the next turn.

If nothing arrives for 10 minutes, the goroutine exits. The next message recreates it.

## Inner monologue: text is thinking, `send` is speaking

This is the key design in Discuss mode.

In Chat, LLM text *is* the reply. In Discuss, we redefined text output as an **inner monologue** — only the bot sees it. The group does not.

To speak, the bot must call the `send` tool. No `send` means silence.

That solves a core problem: **how to let the LLM shut up**. In Chat, the model always generates a reply — that is what it was trained to do. In a group, most messages do not need a bot. If it jumps in on everything, it gets kicked.

By turning "speak" into a tool call, "whether to reply" becomes an action the model can reason about. The system prompt is explicit:

> If you are mentioned or asked a question directly, reply with `send`.
> If you have something genuinely useful to add, reply with `send`.
> If people are chatting, the topic is not about you, and you have nothing to add, stay silent.

Every LLM call also gets a late-binding prompt: "Your text output is an invisible inner monologue. You must use the `send` tool to speak." If the bot was just @mentioned or replied to, that prompt adds: "You were mentioned. You should reply with `send`."

## RC and TR: two orthogonal timelines

Context composition in Discuss is about the relationship between RC and TR.

**RC (Rendered Context)** comes from DCP. It includes every group message — including the bot's own messages after the group has seen them and the pipeline has captured them. Each segment has a `receivedAtMs` timestamp.

**TR (Turn Response)** is the bot's previous LLM calls — assistant output and tool results. Each TR has a `requestedAtMs` timestamp.

Composition is a timestamp merge. When timestamps tie, RC comes before TR, because Anthropic's Messages API requires strict user/assistant alternation: RC is the user role, TR is the assistant role.

That keeps causality straight: the bot sees a message (RC) → reacts (TR) → a new message arrives (RC) → reacts again (TR). The timeline stays correct.

## Chat mode vs Discuss mode

| | Chat mode | Discuss mode |
| --- | --- | --- |
| Trigger | Every message, synchronously | Async goroutine, natural batching |
| Must reply? | Always | Bot decides (`send` tool) |
| What text output means | The reply | Inner monologue, invisible |
| Context source | DB history + current message | DCP pipeline (RC) + past TR |
| Edits / deletes | Unaware | Mutated / marked in IC |
| Group events | Unaware | Renames, membership, and similar enter IC as system events |
| Best for | 1:1 chat, @-triggered replies | Watching a group, joining on its own |

## What's next

Discuss mode already runs in production. A few directions are still in progress:

- **Probe Gate**: before calling a large model, a smaller model decides whether this turn needs a reply. If not, skip the expensive call. The database already has `discuss_probe_model_id`; it is not wired up yet.
- **Cross-session awareness**: let the bot see its state across groups and channels, and connect context more richly.

The idea is simple: don't treat the bot as a tool. Treat it as a group member. Let it hear the whole conversation. Let it decide when to speak. Leave the rest to the model.
