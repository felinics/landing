# Give It a Desktop, and It Can Do More — Introducing Memoh's Workspace Desktop

Many agents are fine in text and on the command line, then stall when they hit a real web page or a graphical UI.

A login flow opens a new window. An upload needs a file picker. Some buttons only exist after the page has rendered. The same page works in a headless browser and gets stuck in real Chrome on styles, permissions, or a dialog. When a user asks "what does this page look like right now?", reading HTML is often not enough.

So we added a desktop to the Memoh bot workspace.

Every Display-capable workspace container can start a visible graphical desktop, with a window manager, a terminal, and headed Chrome/Chromium. You can see it in the web UI. The bot can operate it with tools.

:::tip
"Desktop" in this post means the visible desktop inside a bot workspace. Memoh's Electron desktop app is a different layer: local app UX, hosting the local server, embedded Qdrant, and the CLI.
:::

## Why an agent needs a desktop

The command line is good at deterministic work: files, tests, scripts, APIs. Headless browsers are strong too, for automation, scraping, and page tests.

A lot of real tasks still need the rendered UI.

Real pages have login state, dialogs, drag-and-drop, canvas, complex widgets, permission prompts, file pickers, and state you can only judge by looking. Users also often need to see what the bot is doing, and click once themselves when it matters.

The desktop solves two concrete problems: the bot can drive a real, visible browser; the user can see the same screen.

## Workspace Display: a desktop inside the container

The Memoh workspace desktop runs in the bot's container. It does not control the user's Mac, Windows, or Linux host desktop. Files, commands, network, and tool permissions follow that workspace.

When Workspace Display is enabled, the bridge starts a graphics runtime in the container:

- `Xvnc` provides the X11 display and the RFB input/output channel
- `xfce4` / `xfwm4` / `twm` and similar pieces provide a desktop or window manager
- `xterm` opens a default terminal with the workspace as its working directory
- Chrome/Chromium starts headed and exposes a local CDP port

For the user, that desktop appears in the web UI Display pane. The frontend connects to the display service over WebRTC, shows the live workspace screen, and forwards keyboard and mouse input back into the container.

For the bot, it is a runtime it can operate.

![Opening workspace display in Memoh](/blogs/2026-05-15/desktop-settings.gif)

_The Display pane shows the bot workspace desktop. The browser runs on that desktop._

```text
Bot workspace container
├── files and commands
├── bridge process
├── Xvnc display (:99)
├── terminal
└── headed Chrome / Chromium
    └── CDP on 127.0.0.1:9222
```

The page you see in the Display pane is the same browser the bot drives with Browser Use.

## Browser Use: the same visible browser

If the target is a web page, Memoh prefers Browser Use.

Browser Use talks to workspace Chrome/Chromium over the Chrome DevTools Protocol (CDP). The browser runs headed and shows up in the Display pane.

The agent gets a few tools:

![Driving a headed browser from the Display pane](/blogs/2026-05-15/display-browser.gif)

_The Chrome in the Display pane is the workspace Chrome. You and the bot share the same browser state._

**`browser_observe`**: inspect the current page. It can read an interactive-element snapshot, body text, title, URL, HTML, or take a screenshot — including an annotated one.

**`browser_action`**: act in the browser — open a URL, click, fill an input, press keys, scroll, upload a file, switch tabs.

**`browser_remote_session`**: for Playwright or CDP scripts. The script connects to the same workspace Chrome. You do not start another browser.

The page you see, the page the bot reads, and the page the tools operate are one browser state. If the bot gets stuck halfway, you can see it. After you handle login or a permission prompt by hand, the bot can continue.

## Computer Use: when page semantics are not enough

Browser Use is for DOM, forms, buttons, and navigation. Some UI is outside what CDP understands.

System file pickers, native browser permission dialogs, a crashed page, a non-browser GUI app, or state that only exists as pixels. That is when you need Computer Use.

Computer Use is more direct: screenshot, then move the mouse, click, drag, scroll, type, press shortcuts. It goes through display I/O, not the browser DOM.

A lot of automation dies on those small moves: look at the screen, click the button, press Esc, refocus the window. Computer Use is for that.

Memoh's policy: use Browser Use when you can — it is more stable and more semantic. Fall back to Computer Use when CDP cannot reach the UI.

## Display Pane: keep the user in the room

The desktop should be visible to the user too.

In the Memoh web UI, the workspace area can open chat, draft, file, and terminal — and a display tab. The Display pane checks whether the desktop runtime is ready. If dependencies are missing, it runs a prepare flow on the backend to install or configure the desktop, VNC, browser, and fonts.

Once connected, you see the workspace's primary display.

![Opening a terminal in the workspace display](/blogs/2026-05-15/display-terminal.gif)

_The same Display session can show the browser, the terminal, and other GUI._

That makes a lot of workflows easier:

- the bot is debugging a web UI, and you can see where it clicked
- the bot opens an admin page, you handle login once, then it continues
- the bot reproduces a visual bug, and you can confirm it is looking at the same state
- the bot is on an uncertain UI, and you can take over mouse and keyboard at any time

The benefit is simple: the bot does not have to narrate every state. You can look.

## Why not only headless Playwright

Headless Playwright is useful. We are not replacing it with a desktop.

The split is roughly:

| Capability | Best for | Limit |
| --- | --- | --- |
| Command-line tools | Files, code, tests, builds, scripts | No graphical state |
| Headless browser | Fast web automation, batch tests, deterministic scripts | The user cannot see the run; real login / dialogs / visual state often break the flow |
| Browser Use | Visible Chrome, pages, forms, navigation, screenshots | Mostly in-page browser state |
| Computer Use | Native dialogs, non-browser GUI, coordinate recovery | Less semantic, actions need more care |
| Display Pane | Watch, take over, confirm together | Needs a workspace graphics runtime |

Headless browsers are for scripts and batch jobs. Workspace Display is for tasks where someone needs to see the screen.

## Permissions and isolation

This desktop does not take over the user's computer.

Memoh's desktop runs in the workspace container. Filesystem, processes, network, and tool permissions still follow the bot workspace. The web UI shows that container desktop and forwards user input into it.

It only operates the workspace desktop. The user's system desktop is not on this channel.

For a trusted local workspace, Memoh is more careful: that workspace already runs with host privileges, so the Display pane is not exposed as a normal container desktop by default. Desktop capability is meant first for container workspaces that can be isolated, destroyed, and rebuilt.

## What becomes possible

With a desktop, a lot of previously awkward work gets simpler.

The bot can open a local web service, look at the page, click, screenshot, and find the issue. It can enter a SaaS console and configure a project along steps you already confirmed. It can handle an OAuth flow in a visible browser, with less guessing about redirects and page state. When the UI is unstable, it can send the current screen and let you choose the next step.

You also do not have to guess what the bot did in the background. Open the Display pane.

## What's next

The workspace desktop works today. It is not yet effortless. Next we will focus on:

- **Less friction on first open**: some workspace images lack fonts, some lack a browser, some package mirrors are slow. Display prepare already covers part of this; failures should still explain why, and how to fix it.
- **Make the bot's actions readable**: a click, a keystroke, a screenshot should sit next to the matching tool call. Users should not have to hunt logs to guess where it clicked.
- **Continue after a human takeover**: login, 2FA, and permission prompts often need a person. We want the bot to stop there, wait, then resume from the current page.
- **Finer session permissions**: who can watch the desktop, who can take over input, whether screenshots can go into the current chat, how long a remote CDP session lasts — all of that should be configurable.
- **More stable complex UI**: canvas, drag-and-drop, rich text, file upload, multi-window switching. We will keep adding tests and tool coverage.

A basic bet we make with Memoh: chat is for talking, the command line is for execution, memory is for long-term context, and the desktop is for work that needs a screen.

Give the bot a workspace desktop, and it can open a page, read the state, click a button, try the flow, then tell you what happened.
